# 容器挂载目录权限

容器启动后报 `Permission denied`，绝大多数不是镜像问题，而是**宿主机挂载目录的属主或权限和容器内进程的 UID/GID 对不上**。本文给出通用的判断与修复方法，适用于所有 bind mount 场景。

## 1. 常见现象

同一类问题在不同镜像里报错措辞不同，但都指向挂载目录不可写：

```text
# Redis
*** FATAL CONFIG FILE ERROR ***
Can't open the log file: Permission denied

# MySQL
mysqld: Can't create/write to file '/var/lib/mysql/xxx' (Errcode: 13 - Permission denied)

# Nginx
open() "/var/log/nginx/error.log" failed (13: Permission denied)

# 通用
mkdir: cannot create directory '/data/xxx': Permission denied
```

典型特征：

- 报错路径位于 `volumes` 挂载的目录内
- 容器启动即退出，或反复重启
- 把同一个目录换成 Docker 命名卷后一切正常

## 2. 原理

- **bind mount 直接使用宿主机目录的属主和权限**，Docker 不会修改它，也不会把镜像里同名目录的权限带过来
- 容器内进程以某个 UID/GID 运行，内核只比较数字 ID，容器内的用户名在宿主机上没有意义
- 要创建或写入文件，进程需要对目录有 `w` 和 `x` 权限，对已存在的文件有 `w` 权限
- 父目录缺少 `x` 权限时，即使目标目录本身可写，也会被拒绝
- 命名卷（named volume）在首次创建时会按镜像内目录的属主初始化，所以通常不会遇到这个问题

## 3. 定位步骤

```bash
# 1. 看完整报错和退出码
docker logs --tail 50 <container>

# 2. 确认容器内路径对应宿主机哪个目录
docker inspect <container> --format '{{json .Mounts}}'

# 3. 查容器进程实际使用的 UID/GID
docker exec -it <container> id
# 容器起不来时直接查镜像
docker run --rm --entrypoint id <image>

# 4. 看宿主机目录的数字属主和权限（-n 避免用户名干扰）
ls -ldn /path/to/mounted/dir

# 5. 逐级检查父目录的 x 权限
namei -l /path/to/mounted/dir

# 6. 直接验证该 UID 能否写入
sudo -u '#<uid>' test -w /path/to/mounted/dir && echo writable || echo denied
```

判断依据：第 3 步得到的 UID/GID，如果和第 4 步显示的不一致，且目录权限不允许其他用户写入，就是本文要解决的问题。

常用镜像的默认用户可作参考，但**以 `id` 输出为准**：

| 镜像 | 默认 UID:GID |
| --- | --- |
| `redis:7.x` | 999:999 |
| `mysql:8.x` | 999:999 |
| `nginx:1.x` | 101:101 |
| `postgres`（Debian tag） | 999:999 |
| `postgres`（alpine tag） | 70:70 |

## 4. 修复

核心只有两步：**把目录属主改成容器进程的 UID/GID，再给足属主权限**。

### 4.1 新建目录时直接指定

```bash
sudo install -d -o 999 -g 999 -m 750 /path/to/data
```

`install -d` 会创建目录并同时设好属主和权限，比 `mkdir` + `chown` + `chmod` 少两步，也不容易漏。

### 4.2 已有目录

```bash
# 属主改成容器进程的 UID/GID
sudo chown -R 999:999 /path/to/data

# 权限收紧到属主可读写执行
sudo chmod 750 /path/to/data
```

说明：

- `-R` 要带上。如果日志文件已经被 root 创建过，只改目录属主仍然写不进去
- `750` 表示属主 `rwx`、同组 `r-x`、其他人无权限，对大多数服务足够
- 多个容器需要共用同一目录时，用共同组 + `2770`（`setgid` 让新建文件继承组），不要直接放宽到 `777`
- `chmod 777` 只建议在排错时临时验证「是不是权限问题」，确认后立刻改回

### 4.3 不想改属主：用 ACL

```bash
# 授予指定 UID 读写执行
sudo setfacl -R -m u:999:rwx /path/to/data

# 让后续新建的文件也继承该 ACL
sudo setfacl -R -d -m u:999:rwx /path/to/data
```

适合目录还有其他用途、不希望把属主整体改掉的场景。

## 5. 完整处理模板

以任意服务为例，按顺序执行：

```bash
# 1. 从报错里拿到容器内路径，再从 inspect 找到宿主机路径
docker inspect <container> --format '{{json .Mounts}}'

# 2. 查镜像运行用户
docker run --rm --entrypoint id <image>

# 3. 改属主和权限（假设查到 999:999）
sudo chown -R 999:999 /host/path
sudo chmod 750 /host/path

# 4. 重启并观察
docker compose up -d --force-recreate <service>
docker logs -f <container>
```

## 6. 验证

```bash
# 日志不再出现 Permission denied
docker logs --tail 100 <container>

# 容器内实际写一次
docker exec <container> sh -c 'touch /mounted/path/.perm-test && rm /mounted/path/.perm-test'

# 重启后业务数据仍在
docker compose restart <service>
```

## 7. 注意事项

- **SELinux 环境**（Rocky / CentOS 等）：属主和权限都正确仍报 denied 时，检查 `getenforce` 和 `ls -Z`，需要在挂载项上加 `:Z`（或与其他容器共享时用 `:z`），例如 `./data:/data:Z`
- **Docker Desktop（macOS / Windows）**：bind mount 的属主由虚拟机层映射，容器内执行 `chown` 不会反映到宿主机，这类环境优先用命名卷
- **NFS 挂载**：服务端开启 `root_squash` 时，root 会被映射成 `nobody`，`chown` 看似成功但实际无效，需要在 NFS 服务端调整导出参数
- **rootless Docker / `userns-remap`**：容器 UID 会映射到宿主机的 subuid，直接 `chown 999` 不生效，需要按映射后的宿主机 UID 设置
- 目录属主改了之后，原有数据文件的属主也要一起改，否则「目录可写、文件不可读」的问题依然存在
- 纯数据场景优先使用命名卷，可以让 Docker 自己处理属主，从根源上避开这类问题
