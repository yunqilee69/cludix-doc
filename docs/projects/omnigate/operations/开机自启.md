# 开机自启

`omnigate autostart` 与管理台「设置 → 开机自启」共用同一套实现，支持 Linux、macOS、Windows 三端用户级自启。

## 命令

```bash
omnigate autostart install     # 注册开机自启
omnigate autostart status      # 查看状态
omnigate autostart uninstall   # 取消开机自启
```

## 各平台落点

| 平台 | 机制 | 位置 |
| --- | --- | --- |
| Linux | systemd user unit | `~/.config/systemd/user/` |
| macOS | LaunchAgent plist | `~/Library/LaunchAgents/` |
| Windows | HKCU Run 键 | 当前用户注册表 |

## 注册内容

自启进程的工作目录由系统决定（`$HOME`、`/` 或 `System32`），所以注册时必须写入本实例的真实绝对路径：

- `--db`、`--config`、`--log` 都会展开成绝对路径
- 实例名由数据库路径派生，保证「注册的单元」和「实际运行的实例」对得上
- 远程数据库实例必须把 `database.dsn` 写进 `config.yaml`，通过 `--config` 给出；连接串不会进入 systemd unit / launchd plist / Windows 注册表

## 托管进程的行为

托管单元带 `Restart=on-failure`（launchd 为 `KeepAlive(SuccessfulExit=false)`）。因此：

- 在服务运行中点「开启自启」时，被拉起的进程发现 PID 已被占用，会以退出码 0 结束，避免管理器每 3 秒重拉一次形成重启风暴
- 手动 `omnigate start` 撞 PID 时仍以非零码退出，脚本可以据此判断

托管进程会注入 `OMNIGATE_SUPERVISED`。这个标记同时用于：

- 更新后以非零码退出，交给 systemd / launchd 拉起新二进制
- 区分「托管的重复启动」与「用户手动启动」

## 只读命令

`status` 与 `uninstall` 不会在用户主目录里顺手生成 `config.yaml`：它们只读已有配置，文件缺失时使用默认值。

## macOS 的 uninstall

macOS 取消自启用的是 `launchctl disable` + 删除 plist，而不是 `bootout`：

- `bootout` 会立刻杀掉该 label 下的进程。在服务里点「关闭自启」时，那正是当前应答请求的进程，响应还没写完就会被自己杀掉
- `disable` 写入持久禁用记录，下次登录不再加载，当前实例继续运行
- 因此 `status` 只根据 plist 是否存在判断 `Enabled`；本次登录内作业仍会留在 launchd 里，直到注销

## 与版本更新的配合

自启托管的进程更新后自动重启；手动前台进程（例如 `start.sh` 开发实例）不做自动重启。详见 [版本更新](./版本更新)。
