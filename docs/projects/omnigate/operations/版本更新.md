# 版本更新

OmniGate 会检查 GitHub 最新 Release，管理台顶栏显示当前版本，发现新版本打红点。CLI 对应命令：

```bash
omnigate update            # 检查并更新
omnigate update --check    # 只看有没有新版本，不安装
```

## 渠道

| 渠道 | 行为 |
| --- | --- |
| npm 全局安装 | 走 npm 全局升级 |
| 独立二进制 | 下载对应平台归档，校验后原地替换可执行文件 |
| Windows | **不提供一键更新**：运行中的 exe 不可替换，按提示手动下载 |

归档下载沿用 npm postinstall 的双源策略：GitHub ↔ `cdn.yunke.icu` R2。可通过 `OMNIGATE_USE_CDN=1`、`OMNIGATE_GH_PROXY` 控制。

**校验和只认官方源、不回退镜像**。归档与哈希若同出一个镜像，sha256 只能挡传输损坏，挡不住镜像投毒；官方不可达时宁可更新失败。

## 一键更新的安全顺序

1. 下载归档
2. 校验 sha256（条目缺失或哈希不符一律拒绝）
3. 解压
4. 写同目录临时文件，`fsync` 后 rename 上位
5. 旧版改名为 `.bak`
6. 进程重启

临时文件任一步失败都会删除半成品，并清理 1 小时以上、进程被杀的残留 `.new-*`。同目录可能另有实例在更新，较新的残留不动。

## 更新后的重启

| 运行方式 | 行为 |
| --- | --- |
| 后台守护进程 | 拉起 `start --wait-pid <旧PID>` 助手，等旧进程释放端口后启动 |
| 开机自启托管 | 以非零码退出，由 systemd `Restart=on-failure` / launchd `KeepAlive` 拉起新二进制 |
| 手动前台进程 | 不自动重启，只提示手动重启 |

## 版本比较

- 当前版本是本地构建的 `dev` 时，semver 解析失败，**不亮红点**，避免开发期被常驻红点骚扰
- `CanApply` 仍为 true，保留手动安装最新发布版的能力
- 同号预发布（`v1.1.0-rc.1` vs `1.1.0-rc.1`）不视为升级目标

## 查询缓存

服务端缓存查询结果：成功 1 小时、失败 5 分钟。未认证的 GitHub API 只有 60 次/小时，缓存是为了避免打满。

GitHub API 与 `github.com/releases/latest` 的 302 是两条独立通道，API 被限流时靠后者拿 tag。

管理台「重新检查」按钮带 `?force=1`，不受 `update.auto_check` 开关限制；自动检查默认开启，是本工具唯一的默认出站「打卡」请求。

## 相关环境变量

```bash
OMNIGATE_UPDATE_API_BASE=https://api.github.com
OMNIGATE_UPDATE_GITHUB_BASE=https://github.com
OMNIGATE_UPDATE_CDN_BASE=https://cdn.yunke.icu/omnigate
OMNIGATE_USE_CDN=1
OMNIGATE_GH_PROXY=https://镜像前缀
```

## 更新失败怎么办

1. 先看 `~/.omnigate/omnigate.log` 里的错误
2. 官方源不可达时，换网络或代理后重试；不要为了成功而改用镜像校验和
3. 更新后进程没起来时，检查端口是否仍被旧进程占用，再执行 `omnigate status`
4. 需要回滚时，同目录的 `omnigate.bak` 是上一版二进制
